# Norea Content Server architecture

This document describes the current architecture and operational boundaries.

## Purpose

Norea Content Server is an optional secondary copy of content and portable app
state. Norea remains usable without it. The server helps devices reuse content
that another device already acquired and provides explicit cross-device state and
backup services.

The server does not scrape source sites, execute source plugins, or receive source
cookies. New source acquisition stays in the Norea app.

## Components

- **Fastify service** — REST API, authentication boundaries, streaming transfers,
  long-poll/change feeds, and the built-in administration console.
- **SQLite** — catalog metadata, devices, change journals, migration/reconciliation
  state, user-state revisions/receipts, and operational metadata.
- **Filesystem storage** — chapter packages, work metadata/covers, backups, and
  other large byte payloads.
- **Norea clients** — own local reading, downloads, source access, and the sync
  scheduler.

A deployment runs one server process against one data directory. External access
uses a TLS reverse proxy.

## Identity

Portable content identity is source-owned rather than device-local:

- work: plugin ID + source novel ID + source-relative novel path,
- chapter: work identity + source-relative chapter path, with chapter number used
  only where the protocol explicitly allows recovery/reconciliation,
- local/recovered content: validated opaque identities when no original source
  identity can be reconstructed safely.

Local SQLite row IDs are never cross-device identities.

## Access

There are two credential classes:

- **device key** — random per-server credential generated by the app; stored as a
  hash on the server; may be blocked by an administrator,
- **console session** — issued after login with the installation secret stored in
  `admin-password.hash`.

Anonymous catalog/download access is configurable. Mutations and private state
require an admitted device or console credential as appropriate.

## Content synchronization

Content sync is incremental and catalog-driven.

1. Clients read catalog/work change cursors.
2. Local stored chapters are discovered from the durable local journal plus
   bounded reconciliation for content predating that journal.
3. Upload candidates are fingerprinted and compared with server state.
4. Upload conflict policy decides whether an existing server copy is retained or
   replaced.
5. Server downloads install through staged, validated storage operations.
6. Deletions/restores propagate as explicit catalog events rather than deleting a
   device's local reading data.

Catalog browsing is separate from package download. Metadata-only works and valid
incomplete packages remain visible; completeness reports media availability
rather than access permission.

## Work metadata and covers

Work metadata and covers are synchronized separately from chapter bodies. The
filesystem metadata contract preserves source identity, work details, canonical
chapter listings, and cover metadata. Clients validate exact identity before
using recovered files.

## Migrations and chapter-number reconciliation

Work migration and chapter-number correction use durable server records and
proofs. A client applies a change only when the expected lineage and current
identity still match. Conflicts remain explicit instead of guessing titles,
paths, or chapter identities.

See [work-migration.md](work-migration.md) and
[chapter-number-reconciliation.md](chapter-number-reconciliation.md).

## Shared user state

Shared user state is independent of content availability. Durable entity records
and ordered revisions preserve library/category edits, reading tuples, bookmarks,
resume state, and chapter compositions even when a receiving device lacks the
matching content row.

Uploads use idempotent operation IDs and durable receipts. Clients advance by
revision cursor and may defer local projection without losing the shared record.

See [user-state.md](user-state.md).

## Reading state compatibility

The older reading-state API remains available for compatible clients and is
separate from the newer shared user-state lane. See
[reading-state.md](reading-state.md).

## Device backups

A device backup is an opaque archive published under a device name with a
SHA-256 digest. Upload is staged and atomically replaces the prior archive only
after validation. Listing and restore require an admitted device credential.

See [device-backups.md](device-backups.md).

## Storage and durability

- SQLite changes use transactions and durable journals.
- Large files are staged before publication.
- Readers validate the same file descriptor/path from inspection through the
  final read to prevent symlink or replacement races.
- Interrupted publication must leave either the previous valid object or a
  recoverable staged state.
- Database and package files must be backed up as one logical server state.

## Deletion

Local deletion and server deletion are distinct. Server deletion is a soft
catalog operation first; purge is an administrative retention action. A valid
device or administrator can restore content while retained package data remains
available.

## Operational invariants

- Server failure never blocks local reading.
- A device credential never grants console privileges.
- Source credentials never reach the server.
- Unknown or ambiguous identities are retained/deferred or rejected, never
  guessed.
- Invalid archives, unsafe paths, oversized payloads, and incomplete publication
  are rejected before becoming current state.
- Change cursors are monotonic and retry-safe.
- Existing deployed SQLite data is upgraded additively; it is not reset to make a
  release fit.
